# Command reference: `hiraku` and `hiraku-agent`

See `cli.md` for how these two CLIs relate to each other and to the Python
API underneath them. This file just lists what each command does.

Conventions shared by both CLIs: every read/list command accepts `--json`
for machine-readable output (`hiraku`'s own `_emit_json`/`_table` helpers
decide the plain-text rendering otherwise); a domain error (missing task,
bad identifier, agent failure, ...) prints as `Error: <message>` and exits
non-zero rather than a traceback; `HirakuConfig.discover()` finds the
project root from the current directory, so every command below can be run
from anywhere inside a `hiraku` project.

## `hiraku`

### Project

| Command | Does |
| --- | --- |
| `hiraku init [PATH] [--tracking-backend NAME] [--template DIR \| --example NAME] [--ignore-git]` | Initialize a `hiraku` project at `PATH` (default: cwd). |
| `hiraku status [--json]` | Show project root, active task/experiment, default program, tracking backend, current git branch. |

### `hiraku task` — task records and the active task

| Command | Does |
| --- | --- |
| `hiraku task create TASK_ID [--goal] [--question] [--summary] [--markdown-file PATH] [--set KEY=VALUE ...] [--branch NAME] [--no-set]` | Create a task, its git branch, and (unless `--no-set`) make it active. |
| `hiraku task list [--columns c1,c2,...] [--json]` | List tasks (default columns: `id, summary, branch`). |
| `hiraku task show [TASK_ID] [--json]` | Show a task (defaults to the active task). |
| `hiraku task update [TASK_ID] [--goal] [--question] [--summary] [--markdown-file PATH] [--set KEY=VALUE ...] [--unset KEY ...]` | Update and re-validate a task. |
| `hiraku task edit [TASK_ID]` | Open the task's Markdown file in `$EDITOR` (default `vim`), then re-validate. |
| `hiraku task delete TASK_ID` | Delete a task that has no experiments. |
| `hiraku task set TASK_ID` | Set the active task. |
| `hiraku task entrypoints [TASK_ID] [--json]` | List a task's own entrypoint declarations. |

### `hiraku experiment` (alias `hiraku exp`) — experiments and the active experiment

An experiment with no `--commit` is a **proposal** (`Experiment.is_proposal`);
this is also what a `hiraku_agent.Node` is before it has code bound to it.

| Command | Does |
| --- | --- |
| `hiraku experiment create EXPERIMENT_ID [--task ID] [--summary] [--hypothesis] [--commit REF] [--branch \| --branch=NAME \| --branch-name NAME] [--from REF] [--markdown-file PATH] [--set KEY=VALUE ...] [--no-set]` | Create an experiment under a task (defaults to the active task), optionally binding a commit and/or creating its git branch. `EXPERIMENT_ID` may be `task:id` to name the task inline. |
| `hiraku experiment list [--task ID] [--columns c1,c2,...] [--json]` | List a task's experiments (default columns: `id, summary, commit, branch`; commit values are shown abbreviated). |
| `hiraku experiment show [EXPERIMENT_ID] [--task ID] [--json]` | Show an experiment (defaults to the active one). |
| `hiraku experiment update [EXPERIMENT_ID] [--task ID] [--summary] [--hypothesis] [--commit REF] [--markdown-file PATH] [--set KEY=VALUE ...] [--unset KEY ...]` | Update and re-validate an experiment. This is how a proposed node gets its commit bound — the "implement" step in `hiraku-agent next`'s suggestions. |
| `hiraku experiment edit [EXPERIMENT_ID] [--task ID]` | Open the experiment's Markdown file in `$EDITOR`, then re-validate. |
| `hiraku experiment delete EXPERIMENT_ID [--task ID]` | Delete an experiment record. |
| `hiraku experiment set EXPERIMENT_ID [--task ID]` | Activate an experiment (and its task). |
| `hiraku experiment clear` | Clear the active experiment. |
| `hiraku experiment entrypoints [EXPERIMENT_ID] [--task ID] [--json]` | List the experiment's effective entrypoints (its own, merged over the task's). |

### `hiraku proposal` — read-only view over unbound experiments

| Command | Does |
| --- | --- |
| `hiraku proposal list [--task ID] [--json]` | List experiments in a task that have no commit yet (i.e. every `is_proposal` node). |

### `hiraku program` / `hiraku context` — generic record CRUD (data model only — see below)

Both generated by the same `_install_record_group()` helper, so both have
exactly the same six commands:

| Command | Does |
| --- | --- |
| `hiraku program create PROGRAM_ID [--markdown-file PATH] [--set KEY=VALUE ...]` | Create a program record. |
| `hiraku program list [--json]` | List program ids. |
| `hiraku program show PROGRAM_ID [--json]` | Show a program record. |
| `hiraku program update PROGRAM_ID [--markdown-file PATH] [--set KEY=VALUE ...] [--unset KEY ...]` | Update and re-validate a program record. |
| `hiraku program edit PROGRAM_ID` | Open in `$EDITOR`, then re-validate. |
| `hiraku program delete PROGRAM_ID` | Delete a program record. |

`hiraku context ...` has the identical six commands over `Context` records.
There is deliberately no `hiraku context set` / "active context" — that is
not an oversight in this doc, it does not exist in `HirakuConfig` today
(compare `active_task_id`/`active_experiment_id`).

**`Program`, `Action`, and `Context` (`hiraku.agent`) are data-model-only in
this version — nothing executes them, and `hiraku_agent` does not read
them.** Per `hiraku`'s own `docs/concepts.md`: "Version 0.1.0 only
implements the data model and not yet the agent integration." Concretely:

- `Program` (`hiraku.agent.Program`) is meant to define "complex research
  workflows and loops end-to-end, with defined permissions and limits" — an
  end-to-end policy wrapping *many* steps, closer in spirit to "keep calling
  `hiraku-agent next` and whatever it suggests, under a budget, until
  `exhausted`" than to any single `hiraku-agent` command. But the class
  itself is `class Program(Record): """An editable agent program
  record."""` — no permission/limit/checkpoint fields, and no code
  anywhere interprets one. `hiraku program create/show/...` today just
  stores a named Markdown file at `hiraku/programs/<id>/program.md`.
- `Action` (`hiraku.agent.Action`) is meant to be "one-step execution
  patterns that combine deterministic hooks with LLM instructions and have
  a validated start and end state" — that description is at the same
  granularity as one `design`/`discover`/`triage`/`analyze` call, and
  conceptually a finished version of this feature might have
  `hiraku-agent design` load a per-project, per-entity `Action` record
  (`{entity}/{action_id}`) to customize its instructions. **It does not
  today.** `hiraku_agent`'s four workflows are hardcoded Python
  (`workflows.py`) with their own prompt templates
  (`hiraku_agent/prompts/*.md`, optionally overridden per project at
  `.agents/skills/hiraku-agent/{workflow}.md` — see `engine.build_prompt`'s
  docstring); confirmed by grepping `hiraku_agent`'s source, nothing in it
  imports `hiraku.agent` at all. They are two independent things that
  happen to operate at a similar granularity, not two names for the same
  mechanism.
- `Context` (`hiraku.agent.Context`) is meant to hold "curated context
  files, e.g. literature, cross-task summaries, etc." — i.e. exactly what
  you'd guess: existing project background, references, prior findings,
  kept as a named, reusable record. That is a different mechanism from
  `hiraku_agent`'s own `--context PATH` option on `design`/`discover`/
  `triage`/`analyze` (documented above), which **is** implemented and
  working today: it reads the exact files you name, verbatim, fresh on
  every call (`engine.gather_context`), with no curation, summarization, or
  persistence between calls. If what you want is "hand the agent this
  literature review every time," today's working path is `--context
  path/to/review.md` on each `design`/`discover` call (or scripting it via
  the Python API — see `cli.md`) — not `hiraku context`, which nothing
  currently reads.

| `hiraku action update ENTITY/ACTION_ID [--markdown-file PATH] [--set KEY=VALUE ...] [--unset KEY ...]` | Update and re-validate an action record. |

| `hiraku action delete ENTITY/ACTION_ID` | Delete an action record. |

### Launching and runs

| Command | Does |
| --- | --- |
| `hiraku launch TARGET [-- ENTRYPOINT_OVERRIDES...] [--task ID] [--commit REF] [--dispatch NAME] [--dry-run]` | Resolve an entrypoint (`TARGET` is `name` or `experiment_id:name`) and launch it. `--dry-run` prints the resolved dispatcher and command instead of running them. |
| `hiraku run list [--task ID] [--experiment ID] [--metrics a,b] [--params a,b] [--sort NAME] [--ascending \| --descending] [--limit N] [--json]` | List normalized tracked runs for a task or one experiment. |

## `hiraku-agent`

Every `design`/`discover`/`triage`/`analyze` command shares one set of
agent-calling options (`_AGENT_OPTIONS` in `hiraku_agent/cli.py`):

| Option | Does |
| --- | --- |
| `-m, --instruction TEXT` | Extra steering text folded into the prompt as "Instruction from the researcher". |
| `--instruction-file PATH` | Read `--instruction` from a file instead. |
| `--agent-cmd CMD` | Override the agent command for this call. Otherwise: `HIRAKU_AGENT_CMD` env var, then the default `claude -p`. |
| `--dry-run` | Build and print the prompt; call nothing, write nothing. |
| `--no-apply` | Call the agent, print/log the reply, but write no `Node` files. |
| `--context PATH` (repeatable) | A project file to read verbatim and offer to the agent as background. Not automatic — nothing is read unless named here. |
| `--timeout SECONDS` | Override the default 900s subprocess timeout. |
| `--unset-env NAME` (repeatable) | Drop this environment variable before invoking the agent (e.g. `--unset-env ANTHROPIC_API_KEY` to force the `claude.ai` login instead of an API key). |
| `--json` | Print the agent's parsed JSON reply instead of the human-readable summary. |

`--context-bytes` (caps how much of each `--context` file is embedded) has
no CLI flag — see `cli.md`'s "Deciding: CLI or Python API" section.

| Command | Does |
| --- | --- |
| `hiraku-agent next [--task ID] [--json]` | Print the single next action for a task and why (`design`, `implement`, `launch`, `analyze`, `triage`, `approve`, or `exhausted`), plus a ready-to-run `hiraku-agent ...`/`hiraku ...` command when there is an obvious one. |
| `hiraku-agent approve NODE_ID [--task ID] --by WHO` | Clear the approval gate on a proposed node. A no-op in `auto` mode. |
| `hiraku-agent design [--task ID] [agent options]` | Propose a tree of experiments for a task. Writes proposed `Node`s (no commit). |
| `hiraku-agent discover [--task ID] [agent options]` | Search for candidate hypotheses (literature or an idea you give it via `--instruction`). Writes accepted ideas as proposed `Node`s and declined ones as `abandoned` `Node`s (so a later `discover` doesn't re-propose them). |
| `hiraku-agent triage NODE_ID [--task ID] [agent options]` | Classify why `NODE_ID`'s result missed its expectation and decide whether to add follow-up child nodes. |
| `hiraku-agent analyze NODE_ID [--task ID] [agent options]` | Judge `NODE_ID`'s runs against its expectation; writes findings/conclusions and, when warranted, a verdict. |

`--task` is required unless a task is already active (`hiraku task set`);
`triage`/`analyze` take `NODE_ID` positionally and resolve its task from the
node reference the same way `hiraku experiment show` does (qualified
`task:id`, or the active task).

### Examples

```bash
hiraku task set vo-backend

# Interactive default: prompts printed on stderr while the agent runs,
# a plain-text summary of what got written on success.
hiraku-agent design

# Preview the exact prompt without calling anything.
hiraku-agent discover --dry-run --context docs/vo-backend-notes.md

# Call the agent, inspect the reply, but don't write Node files yet.
hiraku-agent triage awaiting-node --no-apply --json

# Machine-readable output for another tool to consume.
hiraku-agent analyze leaky-eval --json > analysis.json

# What should I do next, and with what command?
hiraku-agent next --json
```

### Where a call's evidence lives

Every `design`/`discover`/`triage`/`analyze` call is logged under
`<project>/<hiraku_dir>/agent-logs/<timestamp>-<workflow>-<target>/`
(`hiraku_dir` defaults to `hiraku`, so normally
`hiraku/agent-logs/...`):

| File | Contains |
| --- | --- |
| `prompt.md` | The exact prompt sent to the agent. |
| `reply.txt` | The agent's raw stdout, on success. |
| `error.txt` | The exception message, if the call failed (no `reply.txt` in that case). |
| `meta.json` | Command, timeout, dropped env vars, whether web tools were reachable, duration, and (on success) reply length. |

### Node lifecycle, and which command moves it

| State (`hiraku_agent.STATES`) | Meaning | Command that gets you there / past it |
| --- | --- | --- |
| `proposed` | No commit yet. | `hiraku-agent design` / `discover` create it; `hiraku-agent approve` (in `guided` mode) clears the gate; `hiraku experiment update <id> --commit <hash>` binds code. |
| `implemented` | Has a commit, no runs yet. | `hiraku launch <id>:<entrypoint>`. |
| `awaiting_analysis` | Has runs, no verdict. | `hiraku-agent analyze <id>`. |
| `concluded_untriaged` | Has a verdict (`refutes`/`inconclusive`), no children yet. | `hiraku-agent triage <id>`. |
| `concluded_settled` | Verdict is `supports`, or already has children. | Nothing further — `hiraku-agent next` moves on. |
| `abandoned` | Explicitly dropped (`abandoned=True`), e.g. a `discover` idea that got declined. | Terminal; not resumed automatically. |

`hiraku-agent next` computes this same table across a whole task and returns
the single highest-priority action — it is the recommended way to drive the
loop rather than checking state by hand.
